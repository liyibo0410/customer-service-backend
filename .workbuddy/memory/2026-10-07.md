## ⚠️ 两个关键坑（都是本轮踩出来的，务必记住）

### 坑 1：容器不能做成 9:16 —— 场景资源是横图，人像会被裁掉

文档 13 说「官方推荐 540x960（9:16 竖屏）」，**但那个尺寸对这套场景不成立**。

实况：用户魔珐应用里配置的场景是 `litehuman/background_2D/jushen_v1_StudyCorner_01.png`，
**原始尺寸 1920×1080（16:9 横图）**。SDK 内部把背景按
`background-size: cover; background-position: center` 铺满容器 ——
在 9:16 竖容器里，横图会被**左右各裁掉一大半**，而数字人正好站在被裁掉的区域，
结果画面上只剩她的一截手臂（看起来像「没渲染出来」，极易误判）。

**实测四种比例的结果**（容器尺寸→取景）：

| 比例 | 容器 | 结果 |
| --- | --- | --- |
| 16:9 | 638×358 | ✅ 完整全景，人像居中 |
| 4:3 | 638×478 | ✅ 取景最佳，人物更饱满 |
| 1:1 | 558×558 | ✅ 半身近景，可用 |
| 9:16 | 318×567 | ❌ 人像被裁出画面，只剩手臂 |

**结论：这个 SDK 的舞台要用横向比例。本项目最终用 4:3。**

排查手法（值得复用）：把候选比例**逐个真连一次并截图**，不要靠推理。
另外「舞台里只有背景、没有人」时，先单独把场景背景图下载下来看一眼 ——
如果背景图里本来就没人，就说明人像是独立图层，问题在取景不在渲染。

### 坑 2：验证数字人**必须用真 Chrome**，playwright 自带 Chromium 会报 20003

SDK 用 **WebCodecs `VideoDecoder` + `avc1`（H.264）** 解码视频流。
**playwright 自带的 Chromium 不含 H.264 专有编解码器**，于是：

```js
VideoDecoder.isConfigSupported({codec:'avc1.42E01E'})  →  supported: false
// 表现：进度卡在 80%，onMessage 报 code 20003
```

`20003 = PROCESS_VIDEO_STREAM_ERROR`（从 SDK 里挖出来的错误码表，文档没收录）。

**修法**：`executable_path` 指向本机真 Chrome，同时显式声明 WebGL 软件回退：

```python
browser = await p.chromium.launch(
    executable_path=r"C:\Program Files\Google\Chrome\Application\chrome.exe",
    args=["--enable-unsafe-swiftshader", "--use-gl=angle", "--use-angle=swiftshader"],
)
```

换真 Chrome 后：`avc1 支持` → 连接成功 → 发消息 → 状态变「小宝正在说话…」→ 5 秒后回到「数字人在线」。

### ⚠️ 踩到的编码坑（通用，务必记住）

`uv run` 会给子进程设 **`PYTHONUTF8=1`**，于是 Python 进入 UTF-8 模式，
`subprocess.run(..., text=True)` 即使不指定 encoding 也会用 utf-8 去解码。
而中文 Windows 上 `netstat` / `taskkill` 输出的是 **GBK** →

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb3
```

**最坑的是异常抛在 subprocess 的读取线程里**，主线程照常返回，
只看到一段 "Exception in thread Thread-N (_readerthread)"，很容易当成无关噪音忽略。

**修法**：不要用 `text=True`，改用字节捕获后自己挑编码：

```python
raw = subprocess.run(args, capture_output=True).stdout or b""
for enc in ("utf-8", "gbk", "cp936"):
    try:
        return raw.decode(enc)
    except UnicodeDecodeError:
        continue
return raw.decode("utf-8", "replace")
```

顺带一条：`_line()` 里给中文补空格要用**显示宽度**（中文占 2 格），
直接 `f"{name:<12}"` 在终端里对不齐。

### 环境坑（本次新踩，值得记）

1. **`subprocess.Popen` 传 list 给 `cmd /k` 会把内层 `"` 转义成 `\"`，而 cmd.exe 不认 `\"`。**
   症状：`dev_up.py` 里中台窗口「一闪就没」，90 秒后报未启动；而同一函数启动后端却正常
   （因为后端命令 `uv run python main.py` 里没有引号）。
   修法：Windows 分支改成**把整条命令行当字符串传** `Popen(cmdline, creationflags=CREATE_NEW_CONSOLE)`，
   `shell=False` 时 Windows 会把命令行原样交给 CreateProcess。
2. **`mysqladmin ping` 认证失败也返回 exit 0** → compose 的 healthcheck 是**假阳性**，
   容器显示 `healthy` 但密码根本不对（`docker inspect .State.Health.Log` 里明晃晃写着 Access denied）。
   以后判断 MySQL 容器「真健康」要用 `mysql -uroot -p... -e "select 1"`，别信 `mysqladmin ping`。
3. `docker exec $C ls /var/lib/mysql` 在 Git Bash 下会被 MSYS 路径转换吃掉
   （`/var/...` → `C:/Users/.../var/...`）→ 加 `MSYS_NO_PATHCONV=1`。
4. 本会话 `sc.exe` / `reg.exe` 被沙箱黑名单拦截；查 Windows 服务改用 PowerShell
   `Get-CimInstance Win32_Service -Filter "Name='MySQL80'"`，且 **PowerShell stdout 不回传，
   必须把结果 `Set-Content` 到文件再用 Read 读**。
5. 本机原生 MySQL80 的 datadir 是
   `D:\software\ProgramData\MySQL\MySQL Server 8.0\Data`（服务 `MySQL80`，StartMode=Manual，
   当前 Stopped）。`D:\mysql-data` / `D:\mysql-data-cs` 是**别处的**数据目录，不是它的 ——
   别被这俩目录误导（`mysql-data-cs` 里的 `customer_service` 是空库）。

### 端到端验证（改完实测，全绿）

`uv run python tools/dev_up.py` 一键拉起 → 4 端口全就位：3307 MySQL / 18081 中台 /
18082 后端 / 5173 前端。经 **Vite 代理**（与浏览器同链路）实测：

- `GET /commerce/users/u1001/orders` → **200**（真实订单 iPhone 15 Pro 等）
- `GET /commerce/users/u1001/products` → **200**
- `GET /api/chat/history?sender_id=u1001` → **200**（11 条真实历史）
- `POST /api/chat {"text":"你好"}` → **200**，LLM 真实回复「你好呀！今天过得怎么样？想聊点什么呢？」

**注意**：从工具沙箱里 spawn 的 18081/18082 会在工具调用结束时被回收，
要给用户长期使用必须让他自己跑 `start-dev.bat`（或 `uv run python tools/dev_up.py`）。

### 顺带修掉的两个真实缺陷

1. **图片加载失败会留空灰框**
   原来 `@error="$event.target.style.display='none'"` 只把 `<img>` 藏掉，`v-else` 占位图标**不会出现**（因为 v-if 判的是 `cover_url` 有没有值，不是加载成没成功）。
   → 新增 `failedImages` ref + `markImageFailed(url)`，4 处图片统一改成
   `v-if="... && !failedImages[url]"` + `@error="markImageFailed(url)"`，失败即回退到 SVG 图标占位。
   触发场景真实存在：课程数据的 `cover_url` 全是外链 `https://placehold.co/400x400/...`。

2. **历史消息里的对象卡与实时不一致（丢封面图 + 状态退化成文字）**
   对象卡有**两种 payload 形状**：
   - 实时消息（`appendUserObject`）→ 扁平业务对象，`cover_url` / `status` / `amount` 在**顶层**
   - 历史消息（`appendMessage`）→ `{ type, id, title, attributes: {...} }`，值全在 **`attributes` 里**
   模板只按扁平形状取值（`payload.cover_url`、`payload.status`），所以历史卡没图、状态显示成 `订单状态：待发货` 这行文字而不是徽章。
   辅助函数 `getObjectAmount/getObjectSummary` 本来写了 `payload.x ?? payload.attributes?.x` 兜底，**模板漏了**。
   → 在 `appendMessage` 里把两种形状归一：`payload: { ...(object.attributes ?? {}), ...object }`，一处修复同时解决图与徽章。
